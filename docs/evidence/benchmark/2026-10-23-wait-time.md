# Where a study run waits, 2026-10-23

This report times a real one-participant study end to end, phase by phase, three times on a remote
runner and three times with `--local`. It then times the default analyst and two faster settings
on the saved recordings from [analysis models on fixed recordings](2026-10-22-analysis-models.md).
All times are seconds of wall time.

## A study run, phase by phase

The study is the 0.145.0 release smoke study: one desktop participant on the movie game, mission
"play one round, then say whether you would come back", with automatic analysis on the default
analyst (`gpt-6.1-sol`, medium effort). Each run was `npx humanish run remote-smoke --json
--no-open` from humanish 0.145.0 installed from npm, with `--local` added for the local runs. The
six runs went one after another between 18:43 and 19:04 UTC. Every stderr line got a timestamp as
it arrived. The other timestamps come from the run bundle: `sandbox-receipts.ndjson` (runner and
desktop created), `events.ndjson` (run created, Chrome DevTools answered), `actor.json` (session
start and end), the analysis attempt's receipt (analysis start and end) and
`analysis-automatic/job.json` (job record written).

Across all six runs the median total is 194 s. The participant session takes a median 86 s, the
analysis 65 s, and the desktop 29 s from creation to session start.

The remote run adds a fixed 17.8 s at the medians: 12.2 s before the run exists (13.1 s against
0.9 s) and 5.6 s after the analysis (6.5 s against 0.9 s). The remote command prints the live
Observer URL 17.0 to 20.3 s after it starts. The session and analysis differ between the modes
because the participant played differently in each run (12 to 22 screenshots, 2,557 to 4,328
analysis output tokens), and n is 3 per mode.

Every run exited 0. `npx humanish reclaim --run <id>` after each run returned `clean`, with each
receipted sandbox `already-gone` (runner and desktop for remote runs, the desktop for local
runs). An E2B sandbox listing after all runs and the install probe below showed 0 running
sandboxes.

### What the runner does before the run starts

`src/remote/launch.ts` and `src/remote/runner.ts` run these steps one after another on every
remote run:

1. `npm pack` of the local humanish into a temporary directory (`packThisHumanish`), 1.4 to 1.7 s.
2. A fresh sandbox from E2B's `base` template (`acquireRunner`), 0.4 to 0.6 s.
3. `installHumanish`: upload the tarball, download Node 22.23.4 from nodejs.org, check its sha256,
   extract it, then `npm install -g` the tarball and `@e2b/desktop`, which resolves and downloads
   every dependency from the npm registry. 7.5 to 11.3 s.
4. `uploadProject`: one `writeFile` call per study file, in sequence, then `startRemoteRun`.
5. `followRemoteRun` reads the runner every 5 s (`POLL_MS`). Each read runs four commands in
   sequence: `cat status.json`, `cat result.json`, `tail watch.err` and `pgrep`.

The install was split into its steps in three fresh `base` sandboxes with the published 0.145.0
tarball:

| Step | Probe 1 | Probe 2 | Probe 3 |
| --- | --- | --- | --- |
| Sandbox created | 0.4 | 0.2 | 0.3 |
| Tarball uploaded | 0.8 | 0.8 | 0.8 |
| Node downloaded | 0.6 | 0.5 | 1.7 |
| Node extracted | 1.6 | 1.4 | 1.5 |
| `npm install -g` of humanish and `@e2b/desktop` | 5.6 | 4.8 | 6.3 |
| `humanish --version` | 0.7 | 0.5 | 0.8 |

The registry install is the largest step, 4.8 to 6.3 s. Node costs 2.0 to 3.3 s. After the run,
the launcher waits up to one poll interval to see the result (2.4 to 4.0 s here), lists and hashes
every file of the run in the runner, and copies each file it does not already have, one at a time
(2.9 to 3.3 s).

### What the desktop does before the session starts

`src/routes/computer-use/e2b-desktop/desktop.ts` prepares a participant in sequence: read the
desktop's resources, verify the screen geometry, place files, provision the subject, start
recording, launch Chrome and wait for DevTools, start network capture, wait
`DESKTOP_SETTLE_MS`, turn off the screen saver, then start the stream and read the browser
geometry. `DESKTOP_SETTLE_MS` is a fixed 8,000 ms sleep (`src/substrates/e2b/desktop-browser.ts`)
for "a cold browser and page load to paint". It starts after DevTools has answered, which took
6.0 to 20.1 s after launch in these runs. From DevTools answering to session start took 10.5 to
13.5 s, so the fixed sleep is 8 s of it.

## Analysis on fixed recordings

Three settings ran one after another on copies of the saved recordings, with the same concurrency
for each: Taskly through `pnpm bench --reanalyze` with 8 analyses in flight, and the movie game
with each of its 3 runs analyzed twice in sequence, 3 in flight. Every analysis used
`--max-output-tokens 32768`; the movie-game calls also used `--max-cost 10`.

- Sol medium is `gpt-6.1-sol` at medium effort, the shipped default.
- Sol medium, verbosity low is the same with `text.verbosity: "low"`, from a scratch build of this
  checkout that added `gpt-6.1-sol` to `OPENAI_TEXT_VERBOSITY` in `src/analysis/models.ts`. The
  bench header recorded "with uncommitted src/ changes" for that setting. The change was reverted
  after the run.
- Sol low is `gpt-6.1-sol` at low effort with the shipped build.

Recall is scored with Taskly rubric version 2. "Request" is the analysis artifact's span from
`createdAt` to `completedAt`, which covers the provider request and validation. Output tokens per
second is output tokens over that span.

Every movie-game analysis passed the evidence checks with status `partial`, because each run
holds more captures than the analysis reads. The first analysis of each run in each setting cost
$0.21 to $0.27 and the second $0.07 to $0.08, from cached input.

All three settings write about 57 output tokens a second on both fixtures. Their wall times
follow the number of tokens they write. Low effort writes 20% fewer tokens on Taskly and 23% fewer on the movie game, and is 20% and 23%
faster. Low verbosity wrote 9% fewer tokens on Taskly and 1%
fewer on the movie game, and its median time moved by 3.3 s and 2.1 s, within the spread.

The 2026-10-22 runs measured Sol medium at 97 s and the verbosity-low build at 63 s on Taskly,
with up to 19 analyses in flight across settings. Today, with 8 in flight and one setting at a
time, Sol medium took 65.7 s. The earlier speed-up from low verbosity did not reproduce here.

### Time to first output and decode

humanish does not record them. The OpenAI wire (`src/analysis/openai-wire.ts`,
`src/analysis/provider.ts`) sends one non-streaming request and reads the whole response. The
recorded `outputTokens` does not separate reasoning tokens from the report. The CLI's progress
lines put the provider request at 84 to 135 s of each movie-game call, and the validation that
follows at 0.004 to 0.007 s.

### Movie game findings against Sol medium

Each setting's finding and design-finding titles were read against both Sol medium analyses of the
same run.

Sol low:

- First run: both Sol medium analyses report that Enter did not submit on the desktop, so the
  player had to Tab or click. One of the two Sol low analyses reports it. The other problems match:
  accidental picks on the phone, the separate confirm step, uncertain round transitions, unexplained
  Daily ties, the picker labeled "Map", the search field moving when a film is picked, and the
  result artwork pushing the next action below the first view.
- Second run: both Sol medium analyses report that status badges crowd the small phone posters,
  and that search results showed confusing or missing titles. Neither Sol low analysis reports
  either problem. Sol low reports the Daily tie wording and the confirm control moving above the
  search field, which Sol medium does not report on that run.
- Third run: the same problems. One Sol medium analysis reports the search field moving on the
  tablet; neither Sol low analysis does.

Sol medium with low verbosity names every problem that Sol medium names on each run in at least one
of its two analyses. It reports the badge crowding in one of two. It adds the phone recap cutting
off the film list on the third run, in both analyses.

This comparison reads titles only. The recordings were not rewatched for these analyses.

## Wall time in the analysis path outside the model call

`analyzeRun` in `src/analysis/service.ts` reads `run.json`, verifies the whole run
(`verifyRunPrepared`, which hashes its files), loads the bundle a second time, selects evidence
and base64-encodes the stored PNG captures (`captureEvidence`), estimates admission, writes the
start receipt, sends the request, validates, writes the artifact and receipt, and re-renders the
Observer (`refreshObserver`).

In the six study runs, session end to analysis start took 1.1 to 2.0 s and analysis end to the
job record 0.4 to 1.3 s. On the Taskly copies, wall time minus the request span was a median 1.6
to 1.7 s.

On the movie-game copies, the CLI took 4.1 to 5.1 s from start to "Analysis admitted" and 4.8 to
6.5 s from "Analysis finished" to exit. Each of those runs already held 14 or 15 saved analyses
from the earlier reports and this one. On one such run, `humanish verify` took 3.8 s with them and 1.2 s
without them, and `humanish observe --no-open` took 6.1 s with them and 1.35 s without them. A
`--dry-run` admission on it took 4.1 to 4.3 s, and `humanish --version` took 0.54 s. Evidence
selection and image encoding were not timed apart from the rest of admission.

## What would cut the wait most

1. Analysis effort. Sol low saves a median 12.9 s an analysis on Taskly and 32.5 s on the movie
   game, at the same pass rate, with 2 fewer of 60 Taskly defects and two problems missed on one
   movie-game run. Low verbosity on Sol medium saved nothing measurable today.
2. Desktop start. The 8 s `DESKTOP_SETTLE_MS` sleep runs after DevTools has answered. A wait on
   the page's load through the DevTools connection that is already open could end sooner. Launching
   Chrome before the 4.0 to 5.3 s of screen checks, file placement and recording start, or beside
   them, would overlap that time with Chrome's 6 to 20 s start. Neither change was built or run.
3. Remote runner setup. A runner template with Node 22.23.4 and humanish's dependencies already
   installed would leave the 0.8 s tarball upload and an install that needs no registry, against
   7.5 to 11.3 s now. A shorter poll after the session, or a wait on the result file, would cut
   the 2.4 to 4.0 s before the launcher sees the result.

## Not verified

- n is 3 per mode for the study runs. The participant played a different round in each run, so
  session and analysis times differ between modes for that reason, and the mode comparison holds
  only for the fixed phases.
- The study runs overlapped the first four analysis settings, one participant and one analysis at
  a time. The verbosity-low movie-game setting ran alone.
- The scratch verbosity build's request bodies were not captured. The setting rests on the source
  edit, the rebuild and the bench header.
- The movie-game comparison reads finding titles. Recall on the movie game is not scored.
- None of the three changes above was built or timed. The savings for changes 2 and 3 are the
  measured durations of the steps they would remove or overlap.
- Time to first output and decode were not measured, because the request does not stream.
- E2B sandbox creation times are from the receipt written after `create` returns, so they include
  the SDK call and not the desktop's boot inside it.
