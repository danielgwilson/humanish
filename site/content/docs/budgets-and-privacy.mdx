humanish is free and MIT-licensed. A live study spends on the providers you bring: a desktop, a model and an analysis call. This page is about controlling that spend, where your keys live, and what is safe to share. [What a study costs](/docs/what-a-study-costs) has the measured numbers.

## Try it without spending

Four steps cost nothing and need no keys:

1. `npx humanish watch` opens the Observer on a bundled sample run. It does not open your app and sends no participant anywhere.
2. `npx humanish run <study> --dry-run` does a dry run of your study without a browser, keys or provider spend, so a mistake in the study file surfaces before a desktop exists.
3. `npx humanish telemetry disable` (or `DO_NOT_TRACK=1`) stops usage telemetry.
4. `review.analysis: false` in the study keeps the analyst call out of the first live run.

## Set a study budget

For the computer-use route, declare both the study budget and a per-participant backstop:

```yaml
caps:
  maxTotalUsd: 4
  maxUsd: 2
execution:
  target: e2b-desktop
  timeoutMs: 600000
```

- `maxTotalUsd` tracks estimated model spend across the study.
- `maxUsd` applies to each participant. Without a study cap, four participants at `$2` each have separate thresholds totaling `$8`; actual spend can exceed that sum.
- Both thresholds are checked after model responses report usage. They do not reserve the cost of the next request. An in-flight model call and concurrent participants can cross a threshold before stopping. They are not hard provider billing limits.
- E2B desktop time, app provisioning, and any services used by your target app are additional. Desktop estimates use dated assumptions; your provider bill is authoritative.
- A model without a known rate cannot satisfy a fail-closed computer-use cap, so the run is refused rather than treated as free.

The included `try-live` study uses one participant, `maxUsd: 2` and `maxOutputTokens: 8192`. It is a starting point for learning the product, not a recommended budget for every task. When `init` finds no OpenAI key and a signed-in Codex or Claude Code, it writes `try-live` with a `local-agent` participant (Codex when it is signed in, otherwise Claude Code) and no dollar cap: account usage has no dollar price humanish can enforce, and the 10-minute `execution.timeoutMs` bounds the run.

The first paid step is this one participant. [Store the keys](#store-credentials) first, then run `npx humanish run try-live` against a synthetic account on the target, with the E2B console open so you can watch the desktop end. Read the bundle's `cost` block and `providerResources` before running a panel.

Supported live runs also request post-run analysis by default. This sends selected
retained text and captures to OpenAI, using `OPENAI_API_KEY`, with a separate $3
admission estimate limit. It is additional to participant budgets and desktop
time, and is not a provider billing cap. Preflight and live-start output disclose
it. Set `review.analysis: false` to disable the request, or configure
`review.analysis.maxCostUsd` to choose another limit. A missing default analysis
key records a skip while preserving a successful recording. So does a default
analysis whose admission estimate is over its limit; the CLI then prints the
`humanish analyze` command that runs it with a sufficient `--max-cost`. An analysis
you declare in the study still fails when its estimate is over its limit. Dry-run and
keyless preview routes make no analysis request.

Analysis usage is stored separately from participant costs. Inspect it with
`humanish analyze list --run latest --json`; unknown usage remains unknown.

```bash
npx humanish stats --study try-live --json
```

Inspect the run's estimated model and desktop costs, rates, and missing-usage fields. An unknown amount means unknown, never zero. A `budget_reached` computer-use session is `incomplete`; reaching a threshold does not establish task completion.

## How cost estimates work

Computer-use bundles carry a per-participant model estimate and an aggregate
E2B compute estimate. Model estimates multiply recorded token usage by a
dated rate table. On the independent computer-use route, each desktop records its
observed CPU and memory and a host-measured span from acquired handle to cleanup.
Different template sizes are priced separately. Every amount is advisory, not an invoice.

The [rate table](repo:src/run/pricing.ts)
records its date, source, and whether a rate is a placeholder. Runtime desktop
estimates use the allocation's resource readback; missing metadata stays unpriced.
The legacy desktop helper uses a labeled 8-vCPU/8-GiB planning assumption, which
is not a provider spending ceiling or a measurement of your template. Inspect
those fields alongside the amount.
An unknown model rate or missing token usage produces `estimatedCostUsd: null`
with a reason; it is never silently counted as zero. Previews invent no spend.

Where the model has separate cache or long-context rates, per-request usage
lets the estimator apply them. Missing usage limits what can be priced; a
complete-looking total is not proof that every provider charge was observed.

Desktop estimates exclude allocation/startup time before humanish acquired the
handle, plan fees, credits, and negotiated enterprise prices. A desktop kept for
debugging or with unconfirmed cleanup adds an unknown remaining-lifetime line,
so its total is marked incomplete. Shared-world participants and their provisioned subject
desktop, a scripted-browser clone's subject desktop, and the terminal sandbox are
priced the same way.

## Choose a model

The `maxOutputTokens` control below requires humanish `0.83.0` or later.

For first-party OpenAI computer-use studies, optional `actor.maxOutputTokens`
sets a positive integer limit on each response's output, including reasoning
tokens. It applies to every participant, continuation and retry. A participant's
first request and a closing report use the smaller of this value and 1024,
and 1024 when it is omitted: a first turn that asks for a screenshot needs a few
dozen tokens. The first request also shows the model the opening screen. The
effective setting is recorded in the actor's `modelSettings`; omitting it keeps
the provider's normal output behavior after the first request.

A reply cut off by this limit runs no action. The same request is sent
once more, after counting the cut-off reply's tokens against your caps, and the
trace notes the retry. If the second reply is cut off too, the participant ends
as `budget_reached` / `incomplete` with `provider_output_limit`; its partial
output does not establish task completion. A small value can therefore end a
session before it produces visible text. This setting does not
bound input/context tokens, total requests, cumulative spend or desktop time.
Terminal, local-agent, scripted, custom-provider/session routes and per-participant
overrides are rejected when they declare this unsupported control.

The default computer-use model is `gpt-5.6-sol`. Set `actor.model` in the study
to pin another supported model. The checked-in rate table also prices models
such as `gpt-5.6-terra`, `gpt-5.6-luna`, and `gpt-5.5`; consult the table in your
installed version instead of assuming a newly available model is priced.

A declared computer-use cap (`maxUsd` or `maxTotalUsd`) on an unpriced model is
refused at preflight with `HUMANISH_COMPUTER_USE_UNPRICED_CAP`, and a shared-world one with
`HUMANISH_SHARED_WORLD_UNPRICED_CAP`. This checks whether a
rate is available; it does not prepay or reserve the next request. An absent cap
is uncapped. A zero threshold can still allow a paid model request before its
reported usage triggers the stop, so `maxUsd: 0` is not a no-provider-call mode.
Desktop provisioning can also incur charges.

A cap is kept from the usage each model reply reports. If a capped participant's
reply comes back without usage, humanish sends that participant no further
request and records `usage_unreported`. A request that stalls or fails in transit
may still have been billed, so humanish counts its worst case against the cap
before sending it again: the previous request's input plus the actor's
`maxOutputTokens`, at the model's rates. The retry happens only when that fits.
Without `maxOutputTokens` the worst case has no bound, so a capped study without
`maxOutputTokens` stops on a stall instead of retrying (`usage_unreported`). The
`try-live` study and the capped studies in `humanish/studies/` set `maxOutputTokens: 8192`
for that reason.

The terminal route reads `caps.maxUsd` for its separate cost-ledger and
product-spend rules; it does not use these computer-use model thresholds. Its
Codex tokens are counted but unpriced, so a live terminal run with a positive
`maxUsd` is refused with `HUMANISH_TERMINAL_UNPRICED_CAP` unless an adapter's
cost probe measures spend. Set `maxUsd: 0` and bound the run with
`caps.maxMinutes`, which stops the agent command. A sandbox may live at most an hour, and
its timeout adds the setup before the agent command (up to 6 minutes, or 11 with
`subject.product.install`) and a 5-minute teardown buffer to `maxMinutes`, so a
live run refuses a `maxMinutes` above 49, or 44 with a product install
(`HUMANISH_TERMINAL_CAPS_INVALID`). The run's cost
summary prices the terminal sandbox's compute time the way it prices a
computer-use desktop, from its span and size; that estimate is not counted
against `maxUsd`. A terminal run that exceeds its spend cap keeps the agent's own
verdict and still fails, with `HUMANISH_TERMINAL_CAPS_EXCEEDED`; the review and
`status.json` name the cap. Every route reads the same top-level `caps` block, and a
key the route does not read is refused when the study is parsed: computer-use and
shared-world read `maxUsd` and `maxTotalUsd`, terminal reads `maxUsd`, `maxJobs` and
`maxMinutes`, so `maxTotalUsd` is not a terminal study budget. Check route warnings
before relying on a field.

## Store credentials

`npx humanish keys set e2b` and `npx humanish keys set openai` store the two keys. [Add two keys](/docs#add-two-keys) covers the store, environment variables and `--dotenv`.

Keep env files and credentials out of version control. Run bundles record provisioned variable names, not their values, and persisted text has known secret values scrubbed. The computer-use model's API key stays on the host; the desktop receives actions, not that key.

Terminal-product studies run Codex inside the sandbox. Their default `execution.runtimeAuth: openai-env` supplies the runtime key to that command, where the participant and its child processes can read and use it. Any credentials you declare for the subject app also enter its sandbox.

For terminal studies, `execution.runtimeAuth: openai-egress` keeps the raw OpenAI runtime key outside the sandbox and authenticates requests through E2B's proxy. Sandbox processes can still make paid requests through that proxy; this option does not impose a provider spending limit. Read the [terminal authentication setup and limits](repo:docs/architecture/terminal-product-route.md#runtime-auth-raw-key-placement-and-remaining-provider-access) before choosing it.

## Use a signed-in coding agent

`actor.type: local-agent` runs the participant on your signed-in Codex or Claude Code plan. E2B still bills for desktops, and a dollar cap does not bound plan usage. [Use a local coding agent](/docs/local-agents) has the setup and limits.

## Review evidence before sharing

Run evidence stays in gitignored `.humanish/`, and no command publishes it. Use synthetic accounts and data, and keep private targets in ignored study files. Run `npx humanish verify --run latest --json` and read the pixels before sharing anything. [Verify before sharing](/docs/read-results#verify-before-sharing) explains the `shareSafety` grades and the redacted export.

## Recover after an interruption

After a crash, run `npx humanish runs`, then `npx humanish reclaim --run YOUR_RUN_ID`, which kills what the run journaled and anything E2B lists with the run's tags. `npx humanish reclaim --check --run YOUR_RUN_ID` asks the same questions and kills nothing. For an interrupted `humanish study check` probe, run `npx humanish reclaim --preflight --json`. [Knowing that cleanup happened](/docs/trust-boundaries#knowing-that-cleanup-happened) explains each receipt and how long a preflight sandbox lives.

## Choose telemetry

Telemetry is on by default and never sends studies, subjects, personas, paths or evidence. `npx humanish telemetry disable` or `DO_NOT_TRACK=1` turns it off; [TELEMETRY.md](repo:TELEMETRY.md) lists every field.
