A study moves your app's screen through several parties. This page names them, says what each receives, and lists the threats the design does and does not cover. Where a behaviour is enforced by code, the sentence links the command or document that proves it; where it depends on a provider's terms, it says so.

## Who sees what

| Party                                 | What it receives                                                                                                | When                                                       | Your control                                                                                                                                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Your machine                          | Keys, the study file, every bundle under `.humanish/`                                                           | Always                                                     | Keys live in a user store with mode `0600` or in an ignored env file; `keys list` prints names only                                                                                          |
| E2B, hosted desktop                   | A disposable Linux desktop running a browser on your target app; the screen; anything you place in that desktop | `execution.target: e2b-desktop`                            | The computer-use participant's model key never enters the desktop. Terminal studies receive a runtime key by default; `execution.runtimeAuth: openai-egress` keeps it on E2B's proxy instead |
| OpenAI, participant model             | Each screenshot, the persona, the mission, and the actions so far, once per step                                | `openai-computer-use`                                      | Choose the model; caps and timeouts bound the number of requests                                                                                                                             |
| OpenAI, analyst                       | Selected retained text and captures from the finished bundle                                                    | Automatic after supported live runs, or `humanish analyze` | `review.analysis: false` disables it; the admission estimate is printed and limited                                                                                                          |
| Codex or Claude Code, signed-in agent | The same screenshots and prompts, through your signed-in agent                                                  | `actor.type: local-agent`                                  | Your plan's terms; the bundle marks usage unpriced                                                                                                                                           |
| Local browser runtime                 | Nothing leaves your machine except your agent's own traffic                                                     | Firecracker guest on Linux, Lima on an M3+ Mac             | The guest is disposable; Docker removes it after the run                                                                                                                                     |
| Your target app                       | Real requests from the desktop's network address, real records the participant creates                          | Every live study                                           | Use synthetic accounts and data; public targets need `policies.allowPublicTargets`; a shared-world public target also needs the `subject.publicTarget` owner attestation                     |
| humanish telemetry                    | Command name, version, OS, outcome category, error code                                                         | Default on                                                 | `npx humanish telemetry disable` or `DO_NOT_TRACK=1`; [every field](repo:TELEMETRY.md)                                                                                                       |

No command publishes a bundle, and `feedback issue` renders a draft and makes no GitHub API call.

## Provider terms

humanish does not control what a provider keeps. These are the providers' own statements, read on 2026-09-29, with the humanish behaviour that decides what reaches them.

- **OpenAI (participant model and analyst).** Each step sends the current screenshot, the persona, the mission and the actions so far; `humanish analyze` sends selected text and captures from a finished bundle. OpenAI's [data controls page](https://developers.openai.com/api/docs/guides/your-data) states that data sent to the API is not used to train or improve OpenAI models unless you opt in, that abuse-monitoring logs are retained for up to 30 days, that approved customers can exclude content from those logs under Zero Data Retention, and that regional processing is available on request. `humanish doctor` cannot tell whether your organization has those controls; check your OpenAI organization settings.
- **E2B (hosted desktop).** Each participant gets its own sandbox, created with a timeout and killed by id when the participant ends; humanish never pauses a sandbox, and E2B's docs say only paused sandboxes are kept. E2B's [privacy policy](https://e2b.dev/privacy) governs what it retains about your account and traffic; it does not state a retention period for a killed sandbox's filesystem, so treat anything placed in a desktop as visible to E2B for as long as their policy allows.
- **Codex or Claude Code (`actor.type: local-agent`).** The same screenshots and prompts flow through your signed-in agent under that plan's terms. The bundle records that the usage is unpriced and nothing else about the account.
- **humanish telemetry.** [TELEMETRY.md](repo:TELEMETRY.md) lists every field sent and every field excluded; `npx humanish telemetry disable` or `DO_NOT_TRACK=1` stops it.

## Store credentials

`npx humanish keys set e2b` and `npx humanish keys set openai` store the two keys. `E2B_API_KEY` and `OPENAI_API_KEY` in the environment work too, and `--dotenv <path>` loads an ignored env file for one command. [Add two keys](/docs#add-two-keys) shows the setup. Keep env files and credentials out of version control. Run bundles record provisioned variable names and never their values, and persisted text has known secret values scrubbed.

`humanish keys set <vendor>` writes to `$XDG_CONFIG_HOME/humanish/keys.env`, by default `~/.config/humanish/keys.env`. The directory is created with mode `0700` and the file with `0600`, opened without following symlinks, and only allowlisted provider names are accepted. The values are plain text; file permissions are the whole protection, and nothing is encrypted at rest. `keys list` prints names only, `keys unset <vendor>` removes an entry, and the E2B CLI's own `~/.e2b/config.json` is read when present. To rotate a key, revoke it at the provider, then run `keys set` again; every persisted humanish text has known secret values scrubbed, so a rotated key does not need a bundle sweep.

The computer-use model's API key stays on the host; the desktop receives actions and never that key. Terminal studies run Codex inside the sandbox. Their default `execution.runtimeAuth: openai-env` supplies the runtime key to that command, where the participant and its child processes can read and use it. `execution.runtimeAuth: openai-egress` keeps the raw OpenAI key outside the sandbox and authenticates requests through E2B's proxy. Sandbox processes can still make paid requests through that proxy, so this option imposes no provider spending limit. Read the [terminal authentication setup and limits](repo:docs/architecture/terminal-product-route.md#runtime-auth-raw-key-placement-and-remaining-provider-access) before choosing it. Any credentials you declare for the subject app also enter its sandbox.

## Knowing that cleanup happened

Four records say what happened to each desktop, and none of them enumerates your account:

- `run.json` lists every sandbox the run created under `providerResources`, with `status` `killed`, `running` (kept on purpose for debugging) or `unknown` (its release was not confirmed) and a `cleanup.reason` that gives the release warning. Each names its sandbox as `[redacted-sandbox-id]` with an `idDigest`: from 0.110 the raw ids are only in the run's `sandbox-receipts.ndjson`, and run records, results and command output name a sandbox by digest. Runs recorded earlier keep raw ids in `run.json`.
- `status.json` adds a `sandbox-cleanup` entry to `outcome.execution.warnings` for each sandbox whose release was not confirmed, naming the participant (or `subject`) and the `humanish reclaim --run <id>` command. A local VM has no receipt, so its entry names the container and the `docker rm --force --volumes <container>` command instead, and automatic analysis records `skipped` with `AUTOMATIC_ANALYSIS_CLEANUP_UNCONFIRMED`. On computer-use, shared-world and scripted runs the run stays `ok`, because the evidence stands and the sandbox has its create-time timeout; a terminal run fails instead.
- `humanish cleanup --run <id>` re-checks and writes `cleanup.json` with `already_clean`, `failed` or `skipped` per resource; it never kills a sandbox itself (`humanish reclaim` does). A resource recorded as live or unknown becomes `failed`, and a failed `cleanup.json` also fails `humanish verify`.
- `humanish reclaim --run <id>` kills the sandboxes an interrupted run journaled in `sandbox-receipts.ndjson` and writes `reclaim-receipt.json` with `killed`, `already-gone` or `kill-failed` for each, naming each sandbox by `sandboxIdDigest`. `already-gone` means `Sandbox.kill(id)` answered `false` or threw a `SandboxNotFoundError`; any other error is `kill-failed`, whatever its message says. Each receipt names its provider (`e2b`; older receipts have none and count as `e2b`). A receipt from a provider this version cannot reach is reported as `unsupported-provider` and nothing is attempted for it. `humanish reclaim --preflight` does the same for the sandboxes interrupted `humanish study check` probes journaled under `.humanish/preflight/`. It leaves a journal whose probe may still be running, including one opened on another host or in another pid namespace, until the probe marks it abandoned or its lease elapses, and the result's warnings say why. With `E2B_DEBUG=true` both forms refuse with `HUMANISH_RECLAIM_E2B_DEBUG` and kill nothing, because the SDK's debug mode answers `Sandbox.kill` with `true` without contacting E2B.

The create-time timeout on every sandbox is the backstop when a kill cannot be confirmed: E2B stops the sandbox, and its metering, when that timeout elapses.

A preflight sandbox also stops on its own. A `public-preview` probe gets each target's readiness budget plus five minutes. A `sandbox-loopback` probe gets the longest its clone and serve steps can take with your study's `serve` and seed-step budgets, including the one retry of the runtime and install steps, plus five minutes, so a preflight does not time out where the run would finish provisioning. A declared `execution.desktop.sandboxTimeoutMs`, or E2B's 60-minute maximum, caps both. Without a declared timeout, a clone probe gets 13 minutes (a clone served as-is), 53 minutes for an npm app that installs and builds, and the 60-minute cap once pnpm or yarn adds its step, where earlier versions gave 10; the receipt is what lets you stop it sooner.

## Reproducibility

A rerun is a new sample, not a replay. What is pinned: the model (`actor.model`, default `gpt-5.6-sol`), the reasoning effort (`reasoningEffort` per actor or per participant, recorded in the bundle), the subject commit for cloned repositories, the humanish version, and the rate sheet date behind every cost figure. What is not pinned: sampling (humanish sets no temperature, so the provider's default applies), the desktop's timing, and the page under test. Transport retries are automatic and bounded: a model request is retried up to three times on `408`, `409`, `429` and `5xx` responses, honouring `Retry-After` up to a cap, and a sandbox create is retried once on a transient E2B error. Every retry stays inside the run's spend cap. The only variance data published so far is the persona-contrast study on the [home page](/#study): five or six runs per cell, and four runs on the control app. Keyboard-first participants reported drawDB's database modal 5 of 5 times and TodoMVC's double-click rename 6 of 6 times, and were blocked by them 3 of 5 and 2 of 6 times. Mouse newcomers reported them 0 of 5 and 0 of 6 times. Every participant on the control app reached the goal, 12 of 12.

## Support and compatibility

The CLI requires Node 22.19 or newer (`engines` in `package.json`). The project has one maintainer, no support contract and no SLA; bugs go to [GitHub issues](https://github.com/danielgwilson/humanish/issues) and vulnerabilities follow [SECURITY.md](https://github.com/danielgwilson/humanish/blob/main/SECURITY.md). The [compatibility policy](https://github.com/danielgwilson/humanish#check-the-compatibility-policy-before-upgrading) says what a release may change: a deprecated name lives at least 30 days and through one minor release, and breaking changes ship together with a migration table. Pin the version in `package.json` and read the release notes before upgrading. Every bundle records the version that produced it, and published studies name theirs.

## What the design protects

- **Keys.** The computer-use model key stays on the host and the desktop receives actions. Provisioned variable names are recorded, values are not, and known secret values are scrubbed from persisted text.
- **Evidence at rest.** Bundles land in gitignored `.humanish/`. Screenshots are full fidelity by default; `policies.redactScreenshots: true` blurs frames at capture, and `humanish export --format bundle --redact-screenshots` produces a separately verified redacted copy.
- **Sharing.** `humanish verify` grades a bundle `share_ready`, `local_only` or `blocked` and fails closed: a bundle that cannot pass every gate is never `share_ready`. The gate detects secret and path patterns, also inside common encodings such as escapes, percent-encoding and base64. A file it cannot read as text, or a screenshot that is not a blurred thumbnail, keeps the bundle `local_only`.
- **Spend.** Per-participant and per-study caps stop runs on the estimate; desktops stop at their timeout; analysis is refused above its admission limit. See [what a study costs](/docs/what-a-study-costs).
- **Resources.** Every desktop is journaled by id; `humanish reclaim --run <id>` stops the ones a crashed run left, and `humanish cleanup` writes an inspection receipt.
- **The repository.** Every release runs a public-surface scan that fails on secret shapes, private names and unapproved binaries, and the package is MIT under `danielgwilson/humanish`.

## What it does not protect

- **Free-form sensitive content in pixels or text.** `verify` finds patterns, not meaning. A screenshot can contain anything your app displayed; review it before sharing.
- **Provider retention and training use.** Screenshots and prompts reach OpenAI, E2B or your agent's provider under their terms. Retention, region and training use are outside humanish's control; [provider terms](#provider-terms) above lists what each states.
- **Egress from the hosted desktop.** The desktop has internet access; the participant can reach any site the mission or the page leads it to.
- **Billing limits.** Caps act on estimates after usage is reported. Your provider dashboard is the only hard limit.
- **The safety of the released code.** Every npm release from 0.15.0 on carries two registry attestations, and `npm audit signatures` verifies them. The npm publish attestation covers the package name, version and registry. The SLSA provenance v1 attestation binds the tarball's sha512 to a run of `.github/workflows/publish.yml` in `danielgwilson/humanish` at the release tag, on a GitHub-hosted runner. Together they show which commit and workflow built the tarball; they say nothing about whether that code is safe.

## Threats worth planning for

1. **Prompt injection from the page under test.** The participant reads the screen and follows it. A hostile page can steer it. Nothing in humanish detects injection. Do not place credentials in a desktop that will visit pages you do not control; on terminal studies prefer `openai-egress`. What a steered participant can reach depends on which model decides its actions:
   - `openai-computer-use`: the desktop. The model key stays on the host, the desktop holds no credentials by default, a timeout and a spend cap bound the run, and the desktop is destroyed afterwards.
   - Claude Code (`localAgent: claude`): a process on your machine, started with `--restricted`, `--tools Read`, `--strict-mcp-config`, `--permission-mode dontAsk` and `--no-session-persistence` in a scratch folder that holds only its screenshots. Read is its only tool and cannot open a file outside that folder. Your user, project and local settings files, their hooks, your MCP servers and your CLAUDE.md do not load; managed (administrator) settings still apply. Its environment keeps `PATH`, `HOME`, `USER`, `LOGNAME`, locale, `CLAUDE_CONFIG_DIR` and proxy variables, and no provider key or `--dotenv` name. humanish reads every message it streams and stops the run with `HUMANISH_CLAUDE_PARTICIPANT_TOOL_REFUSED` on any other tool call. This needs Claude Code 2.1.248 or newer; [local agents](/docs/local-agents#where-execution-happens) has the details.
   - Codex (`localAgent: codex`): an app-server process on your machine, in a scratch folder, with a read-only sandbox, approval policy `never`, web search, skills, agents and configured MCP servers turned off, and one humanish desktop tool; any other tool item stops the request. It keeps your Codex home and configuration, and its environment is the one humanish runs with, which can include provider keys.

2. **Sensitive data captured into evidence.** Use synthetic accounts; enable `redactScreenshots` for studies meant to be shared as-is; keep private studies in ignored files; verify and read before sharing.
3. **A leaked key.** Keys come from the `0600` store, the environment, or an explicitly ignored env file, never from the study. Values are scrubbed from persisted text. Rotate at the provider if a bundle ever shows one.
4. **Runaway spend.** Set both caps and a timeout; they stop on the estimate, so budget the panel with the [worksheet](/docs/what-a-study-costs) and watch the first live run.
5. **An orphaned desktop.** After a crash, `runs`, then `cleanup --run <id>`, then `reclaim --run <id>`. If cleanup cannot be confirmed, the receipt says so and you check the E2B console.
6. **A study that is not what it claims.** Every number in a bundle carries its denominator and its rates' date; subjects cloned from a repository are pinned to a commit; public shared-world targets carry an owner attestation. Studies published on this site name the humanish version they ran on.

## Reporting a vulnerability

Report it privately through [GitHub private vulnerability reporting](https://github.com/danielgwilson/humanish/security/advisories/new), as [SECURITY.md](https://github.com/danielgwilson/humanish/blob/main/SECURITY.md) describes. Include the version, the command, safe reproduction steps and a redacted evidence path.
