A study file is YAML with `schema: humanish.study.v3`. This page lists every field the parser accepts. [How a study works](/docs/concepts) explains the terms on one annotated file, and the [own-app guide](/docs/your-app) builds a complete study for your app.

## Keep study files in one of three folders

```text
humanish/studies/*.yaml          committed studies anyone who clones the project can run
.humanish/studies/*.yaml         ignored local studies
.humanish/local/studies/*.yaml   ignored private or machine-specific studies
```

`humanish run <id>` finds a study by its `id` in these folders. Private repository targets, preview URLs and local variants belong in the ignored folders, and you can run any study file by path:

```bash
npx humanish watch .humanish/studies/local-dogfood.yaml --dotenv .humanish/local/provider.env
npx humanish run .humanish/studies/local-dogfood.yaml --json --no-open
```

`--dotenv` loads values into the humanish process, and the names a study lists in `subject.env` are then passed to its sandbox. The run records those names and never their values. Persisted text is scrubbed for known values and secret patterns, with the [coverage limits described under verify before sharing](/docs/read-results#verify-before-sharing).

## Check a study before you run it

```bash
npx humanish study list --json
npx humanish study show first-run --json
npx humanish study check first-run --json
```

None of the three creates a desktop or calls a model. `study show` prints the resolved study, including the persona text each participant receives. `study check` parses the file and reports problems with code `HUMANISH_STUDY_INVALID`:

- A field the parser does not know fails, and the message lists the known fields at that level and suggests the closest one. A misspelled `runtme` in a participant entry fails with that entry's index.
- A field the study's route does not read fails, and the message names the route, such as "route: preview reads no `caps`; remove the block."
- The `route` must match the subject, `execution.target` and the actor. When they disagree, the message names the route they take.

`study check` and `run` also report two advisory warnings for computer-use and
shared-world participants. Neither warning prevents execution, and runs record
them as `study.warning` events in the bundle:

- **Scripted mission:** `actor.mission`, participant `instruction`, or `tasks[].goal`
  contains a numbered or bulleted step list, chained UI actions, quoted control
  labels, CSS selectors, or a URL other than the subject's entry point. The warning
  quotes at most three matching lines per field and gives a situation-style example.
  Describe the participant's situation and desired outcome so the study can show
  where they would get lost. Scripted-browser and terminal studies and researcher
  criteria in `tasks[].success` are excluded.
- **Missing persona background:** a participant has no assigned persona, its file
  cannot be read, or it has no `background`. Add a short, fictional account of their
  relevant experience and situation. Run `humanish study show <study> --json` to
  see what the participant receives, including inherited persona context.

The tables below give each field's type and its default when you leave it out. "required" means the study fails without it.

## Declare the product in `subject`

`subject.source` says what kind of product the study runs on, and each source takes its own fields. A field set on a source that cannot use it fails at parse.

| `subject.source`   | The product                                                                                                                                  | Routes                                     |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `app-url`          | An app that is already running at `subject.appUrl`.                                                                                          | `computer-use`, `shared-world`, `scripted` |
| `clone`            | Repositories humanish clones, builds and serves inside each hosted desktop.                                                                  | `computer-use`, `shared-world`, `scripted` |
| `local-tree`       | Your working tree, packed and served inside each hosted desktop. Gitignored files, `.env*` files and other secret-shaped files are left out. | `computer-use`, `shared-world`             |
| `desktop-cli`      | A CLI the participant uses in a terminal window on a hosted desktop.                                                                         | `computer-use`                             |
| `terminal-product` | A CLI an agent studies in a terminal sandbox, starting from its public pages.                                                                | `terminal`                                 |
| `local-app`        | A dev server on your machine that your own code drives through the library. The CLI refuses it.                                              | `computer-use`                             |
| `this-repo`        | Nothing runs: the preview writes a sample run.                                                                                               | `preview`                                  |

| `subject.exposure`     | `synthetic`                   | none                                             | Your statement that the app, served at a public sandbox URL during the run, holds only synthetic data. ### Start a cloned app with `subject.serve`

| Field                            | Type          | Default  | Meaning                                                                                             |
| -------------------------------- | ------------- | -------- | --------------------------------------------------------------------------------------------------- |
| `subject.serve.install`          | shell command | none     | Runs once before the build, such as `npm ci`.                                                       |
| `subject.serve.installTimeoutMs` | milliseconds  | 600000   | The install step's time limit. Monorepos can need more.                                             |
| `subject.serve.build`            | shell command | none     | Runs once before the app starts.                                                                    |
| `subject.serve.buildTimeoutMs`   | milliseconds  | 600000   | The build step's time limit.                                                                        |
| `subject.serve.start`            | shell command | required | The long-running command that serves the app. A `shared-world` study's command must bind `0.0.0.0`. |
| `subject.serve.url`              | loopback URL  | required | The address humanish waits on and the participant opens, such as `http://127.0.0.1:3000/`.          |
| `subject.serve.readyTimeoutMs`   | milliseconds  | 180000   | How long the app has to answer at `url` after it starts.                                            |

The commands run inside the sandbox with the same trust as your own scripts. The run records a digest of each one.
Each command runs as its own bash script, so a heredoc may close on the command's last line. When bash cannot parse `install` or `build`, the step fails at once with bash's message.

Each step has `name` (lowercase letters, digits and `-`, at most 40 characters), `command`, `when` (`before-build`, `before-start` or `after-ready`; default `before-start`) and `timeoutMs` (default 300000). |

A `stopWhen` rule sets at least one of `urlIncludes` (text in the URL), `urlPathEquals` (an exact path starting with `/`), `textIncludes` (text on the page) and `appStatePathEquals` (`{ path, equals }`, a value in the app state a custom executor reports). An optional `id` names the rule in the run.

A `dwell` window has `ms`, its length from 1000 to 3600000 milliseconds, and is required. `everyMs` is how often a frame is captured, default 10000. `then` is `continue`, the default, or `stop` to end the session after the window. `when` is a `stopWhen`-shaped condition that opens the window; without it, the window opens after the first observation.

### Let a participant wait for the screen to change

A `computer-use` or `shared-world` turn whose actions are only waits and screenshots, and that asks for some wait time, sends no wait to the desktop. humanish looks at the screen every `idleWaitMs`, at most every 30 seconds on a desktop with speech, and asks the model for the next turn when one of these happens:

- A change on the screen holds still. A 16-pixel tile has changed when at least 3 of its pixels differ by more than 24 in a channel. A change over more than 24 tiles, such as a new row or a page load, counts at a second look half a second after it is first seen. A smaller one, such as a badge or a short label, counts once it has held still for more than 65 seconds, unless a tile within 4 tiles of it ticked or moved with a moving region of more than 24 tiles in those 65 seconds (below).
- The participant hears speech.
- A `stopWhen` rule, a `dwell.when` condition or a task's `success` rule matches what humanish sees.
- The participant's wind-down or end arrives.
- The wait's time passes.

The first such turn is planned to last as long as its waits: `idleWaitMs` for each wait that names no duration, and the named lengths, together up to `actor.maxWaitMs`, or 10 minutes when the study does not set it, and at least `idleWaitMs`. Each further such turn in a row whose time passed with no change holding still, or that a change of 24 tiles or fewer ended, lasts twice as long as the one before, and never less than its own waits, up to the same cap. Any other ending, or a turn with another action, starts again from the first length. A participant that sends one wait per turn at the default `idleWaitMs`, on a screen that never changes, waits 5, 10, 20, 40, 80, 160 and 320 seconds and then 10 minutes at a time: 12 model requests in its first hour and 6 an hour after that, leaving out the model's own time. A fake loop showing a hosted desktop's panel clock at its digit positions gave the same 12 and 6 at each of 8 clock phases. A participant that asks for 1 minute on each turn waits 60, 120, 240 and 480 seconds and then 10 minutes at a time.

On a hosted desktop, in a live hour on a support queue page that gained a row every 10 minutes, an OpenAI participant at the default `idleWaitMs` made 48 and 50 requests in two runs, and each row reached it a median of 7 seconds after it appeared. No wait ended on the panel clock, a spinner or an "Opened N minutes ago" label. OpenAI participants already sent many waits in one turn before this watch, so on that page the watch does not lower the request count; it shortens the time a participant takes to see a change. Codex and Claude Code participants that ask for a 10-minute wait are watched for 10 minutes. An OpenAI participant names a wait in minutes with a `wait_minutes` tool, which it has on every request; a call whose minutes are not a finite number above zero is a wait with no duration, and so is a call to a function it does not have, which is answered that there is no such tool. Each wait's `ui_action` in the trace carries `namedMs` when the wait named its length: the length as named, before any cap.

- A blinking caret, a spinner, a rotating banner, a chart or a video keeps moving, so it does not end a wait, and the next wait grows as it would on a still screen. A large change that stops changing always ends one. Looks are seconds apart, so a blink seen in the same phase at every look can read as still.
- A tile ticks when it changes for the first time, or 30 seconds or more after its previous change. A clock's minutes digit ticks, and so does the number in a "2 minutes ago" label. A small change within 4 tiles of a ticking tile, or of a moving region of more than 24 tiles, does not end a wait: a hosted desktop's panel clock, whose tens-of-minutes digit sits beside its minutes digit, ends none, and neither does the end of a relative timestamp that grows from "1 minute" to "2 minutes". Such a change shows in the screenshot at the end of the wait, up to 10 minutes later by default. Once it has held still for more than 65 seconds, the note names its place, unless more than 24 tiles moved at that last look, when the note says a large part of the screen was changing. A spinner changes at nearly every look, so it does not tick, and a label that appears beside it ends a wait once it has held still for more than 65 seconds.
- humanish does not reload, scroll or move the pointer while it looks. On an app that shows new data only after a reload, the participant reloads as an action and waits in its next turn.
- The next turn's note tells the participant how long it waited and why the wait ended: that the screen changed, that a small part of it changed at a named place, that a large part was still changing at the last look, or that a small change was held back. When the participant's wind-down or end ended the wait, the note gives its length and the clock text that follows says why. It does not say how long the next wait can last, since a participant told that names that length and keeps waiting. The trace records each watch as `watch` on the wait's `ui_action`: how long it could last, how long the turn's waits asked for, why it ended, how many looks it took, and the area of the change that ended it.
- A wait in a turn with another action is sent to the desktop for its length.
- Setting `actor.maxWaitMs` to the same value as `actor.idleWaitMs` stops the growth: on a screen that does not change, each turn that only waits keeps its first length.

## List the participants in `participants`

`participants` takes the forms its route accepts:

| Route          | Forms                                                                              | Default  |
| -------------- | ---------------------------------------------------------------------------------- | -------- |
| `preview`      | a count                                                                            | 4        |
| `computer-use` | a count, `{ count, instruction }` for identical participants, or a list of entries | 1        |
| `shared-world` | a list of at least two entries                                                     | required |
| `scripted`     | refused; set `surfaces` instead                                                    |          |
| `terminal`     | refused; one agent runs                                                            |          |

A study has at most 100 participants, each on its own desktop. How many run at once depends on `execution.concurrency` and on [how many sandboxes your E2B plan runs at once](/docs/what-a-study-costs#set-how-many-sandboxes-your-e2b-plan-runs-at-once). Automatic analysis of more than 16 participants runs in cohorts of at most 16, one request each, and one more request merges them into one report; `study check` gives the expected cost of all of them. A `local-app` subject takes no list. `--count` on the command line overrides a count. Each list entry accepts these fields, and an unknown one fails with the entry's index:

| Field                            | Type                                                     | Default                                                 | Meaning                                                                                                                                                                                                                   |
| -------------------------------- | -------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `participants[].id`              | string, at most 40 characters                            | `lane-01`, `lane-02`, …; `role-01`, … on `shared-world` | Names the participant and its evidence folders. Ids are unique.                                                                                                                                                           |
| `participants[].count`           | positive integer                                         | none                                                    | Makes the entry a group of that many participants, `<id>-01` to `<id>-NN`, which share its other fields. A group needs an `id` of at most 37 characters.                                                                  |
| `participants[].persona`         | persona id                                               | `actor.persona`                                         | This participant's persona file. On `computer-use`, a participant whose desktop fails to start is recorded as failed and the others run. So is a participant whose session ends in a harness error, such as a desktop that stops answering: the run records its reason, and every participant after it starts at its time. If its desktop comes up and it then fails before its session, as when the subject does not build, the others are recorded `blocked` and no other sandbox is created. If its sandbox is never created, the next participant starts alone in its place.

### Give a participant files to upload

A participant on a hosted desktop starts with an empty home folder, so a flow that asks for a profile photo or a signed form needs the file put there first. `participants[].files` copies each file onto that participant's desktop before its session starts, and the browser's file chooser finds it:

```yaml
participants:
  - id: applicant
    files:
      - from: fixtures/photo.png # next to the study file
        as: Downloads/photo.png # in the desktop user's home folder
```

- `from` is relative to the folder that holds the study file; for a committed study that is `humanish/studies/`. A library `runStudy` call has no study file, so its `from` is relative to `cwd`.
- `as` is relative to the desktop user's home folder. Missing folders are created.
- humanish reads every file before any sandbox exists, on a dry run too, and refuses the study when a file is missing, is a folder, a symbolic link or a hard link, or leaves the study's folder. It also refuses a `.env` file, a key or credential file, and anything under `.git`, `node_modules` or `.humanish`, in any letter case: the files the local-tree archive leaves out.
- Each file is at most 10 MiB, one participant's files total at most 25 MiB, and the distinct files a study names total at most 100 MiB.
- An `as` that is absolute, has a `..` or `.` part, starts with `~`, names a path twice or is the folder of another `as` is refused at parse. So is one in `subject/`, where humanish puts a cloned or unpacked app, or on a name starting with `.humanish`, and one that looks like a secret, a local path or encoded text, since the run records it.
- After each copy humanish checks the file's size on the desktop; a file that did not land whole fails that participant before its first turn.
- The participant's stream records `desktopFiles`, each file's `as`, size and sha256. The contents and the `from` path are not recorded.
- Use synthetic files. A file you copy is on a desktop a model drives, and the participant can upload it to the site under study.
- A local browser, local VM or `shared-world` study refuses `files` at parse.

### Start participants over time

A participant starts with the run unless its entry sets `startAfterMs`. A group spreads its members with `startEveryMs`: member k starts at `startAfterMs + (k - 1) × startEveryMs`. In this study two support agents work from the start, and six customers arrive five minutes apart from the second minute:

```yaml
participants:
  - id: support-agent
    count: 2
  - id: customer
    count: 6
    startAfterMs: 120000 # customer-01 at 2 minutes
    startEveryMs: 300000 # then one every 5 minutes, customer-06 at 27 minutes
```

- The latest start is 24 hours. A study of one participant takes no `startAfterMs`, and on `shared-world` with `app-url` the `host` starts with the run.
- `study check` and the run's plan print the first and last start and the most participants at once when every session uses its whole `execution.timeoutMs`. A participant whose start comes while every slot that `execution.concurrency` or [your E2B plan's limit](/docs/what-a-study-costs#set-how-many-sandboxes-your-e2b-plan-runs-at-once) allows is taken waits for the next free one, and the plan says how many wait.
- Each participant's desktop is created when it starts, so a `computer-use` participant due at 3 hours holds no sandbox until then. A `shared-world` study with a `clone` or `local-tree` subject keeps its app's sandbox until the last participant ends, so that sandbox's deadline counts the last start, and a study whose deadline passes the [sandbox ceiling](/docs/what-a-study-costs#set-the-sandbox-lifetime-your-e2b-plan-allows) is refused before anything is created.
- `run.json` records each participant's `arrival`: its `startAfterMs`, and on a live run `scheduledAt` and `startedAt`.
- `--rerun-failed-from` starts the participants it reruns together.

### End a participant at a set time

A `computer-use` participant whose entry sets `endAfterMs` works until that time, on the same clock as `startAfterMs`, and does not run out at `execution.timeoutMs`. In this study a support agent stays on for 4 hours while customers arrive:

```yaml
actor:
  clock:
    timeZone: Europe/London # optional: each turn says the local time
participants:
  - id: support-agent
    endAfterMs: 14400000 # the session ends at 4 hours
    windDownMs: 900000 # told the time left from 3 hours 45 minutes
  - id: customer
    count: 12
    startAfterMs: 600000
    startEveryMs: 1200000
```

- From `endAfterMs - windDownMs`, each turn tells the participant when its session ends and how many minutes are left. The hosted desktop's panel clock shows the time but not the end, so this is how it knows. Without `windDownMs` the wind-down is a quarter of the window from `startAfterMs` to `endAfterMs`, at most 10 minutes: 2 minutes for an 8-minute window, and 10 minutes for any window of 40 minutes or more.
- Waiting is part of the job: before `endAfterMs`, a turn that only waits or takes screenshots counts toward neither the idle nor the no-progress backstop. While the support agent only waits, humanish looks at its screen every 5 seconds and asks the model again within about 6 seconds of a new customer appearing, or when its wait passes with no change holding still. On a quiet queue its waits grow to 10 minutes. A turn of only screenshots or 0 ms waits after another turn of only waits or screenshots is watched as a wait with no length. The first such turn, at the start or after an action, is sent at once. See [let a participant wait for the screen to change](#let-a-participant-wait-for-the-screen-to-change).
- Reloading a page that changes only on reload is waiting too. 20 turns in a row that repeat a recent action on an unchanged screen end a participant without `endAfterMs` as `gave_up`, and do not end this one, unless none of the 20 reached the desktop, as when each reload's desktop command fails. From the 20th such turn, humanish watches the screen after each further repeat before it asks the model again, as after a wait with no length. After that streak, a repeat is watched whenever the turn before it also repeated an action on an unchanged screen, so a new item that a reload shows, or one the participant opens, costs one request with no watch. In a fake loop with a 9-second model reply, a participant that reloads every turn for an hour made 38 requests on a page that never changed and 82 on one that gained an item every 8 minutes, and one that waits every turn on a page that shows each item at once made 55. The trace records the streak as a `repeated an action on an unchanged screen` notice with its turn count and time span, and the review lists it in its gaps.
- The participant does not end its own session before `endAfterMs`. When it tries, the trace records a notice, and its next turn tells it the session is not over and how many minutes are left. A participant that keeps trying, taking no action, is ended by the idle backstop as `gave_up`.
- At `endAfterMs` the participant is asked for its closing report, and the session ends as passed, with `stopCause: scheduled_end` in its trace. The report's summary is the participant's `reason`, as the last message is for a participant that ends its own session. The outcome the report declares is the trace's `declaredOutcome`: its `outcome` field, `reached`, `not_reached` or `blocked`, which OpenAI and Codex participants fill, or else the first line of its summary that is not a `>` blockquote, `REACHED THE GOAL.`, `DID NOT REACH THE GOAL.` or `BLOCKED.`. A declared `reached` keeps the pass and counts the participant as reaching the goal, and `blocked` counts it blocked. A report that declares `not_reached` or nothing counts the participant blocked when its summary describes a blocker. Otherwise it keeps the pass, and the review counts it in `participants.ranUntilEnd` and says it ran until its scheduled end.
- Claude as a `local-agent` participant model cannot be asked for a closing report: its participants end with the scheduled end as their reason and no closing account, and `study check` and `run` warn about it. Codex as a local agent writes one.
- The participant's session lasts its window plus 5 minutes for the closing report, in place of `execution.timeoutMs`, and its sandbox lives that long plus the setup and teardown time. A window whose sandbox would outlive the [sandbox ceiling](/docs/what-a-study-costs#set-the-sandbox-lifetime-your-e2b-plan-allows) is refused before anything is created.
- A participant that waits for a free slot until its `endAfterMs` has passed is skipped: no desktop is created, and its record is `blocked` with the reason. The plan predicts who would be skipped, gives them no slot, and warns, naming them. Its prediction assumes each session holds its slot for its whole session budget. It leaves out the time a desktop takes to set up. Setting up a `clone` or `local-tree` subject can take up to 30 minutes, so a run can skip a participant the plan did not name. A run whose sessions end before their budget may skip fewer participants than the plan named, or none.
- The plan refuses an `endAfterMs` at or before the participant's start, a `windDownMs` without `endAfterMs`, and `endAfterMs` on `shared-world`.
- `study check` prints each participant's window, and the run's plan line shows `end=+<time>`.
- A long window grows the run bundle. The plan estimates it from each participant's window, a model turn every 10 seconds and any dwell window's frames, and `study check` prints the estimate as `bundle size`. A participant without `endAfterMs` is counted for 3 minutes, or its `execution.timeoutMs` when shorter. When a live study's estimated `run.json` passes the 16 MiB analysis reads of it, one participant's trace passes the 32 MiB humanish reads of each trace, its Observer page `observer/index.html` passes the 32 MiB verify reads, or its files pass the 10,000 plus 5,000 for each participant that the public-safety scan reads, `study check`, `humanish run` and `doctor --study` print a warning before anything is created, and the run goes ahead. `run.json` grows by about 16.5 KB a participant, since each model turn's usage rows are only in the participant's trace. It also holds `actor.mission`, the `actor.tasks[].goal` texts and each participant's instruction in that participant's stream, and once more for each participant that reports friction or stops. It holds the first participant's mission, instruction and task goals once more for the run. The estimate counts the copy for friction or a stop for every participant, so it warns at 100 participants with about 75 KB of these texts each, and its advice names the field with the most bytes. A turn adds from about 0.8 KB to 3.3 KB to its participant's trace on the live runs measured, more for a participant that takes many actions a turn, and the estimate counts 3.5 KB. The Observer page carries every participant's trace items gzipped, so busy participants grow it faster than `run.json`. 19 participants working 8 hours fit, with the page at about 31 MiB and `run.json` at about 0.3 MiB. At 20 the page passes the verify limit, and verify then cannot scan it, so the run grades `local_only`: `humanish export` refuses it without `--local-only`, and `humanish export --format bundle` fails. The page carries each participant's items compressed on their own, so it builds when the traces together pass 512 MiB, the longest string Node holds: `humanish observe` wrote it for 25 participants with 30 MiB traces. Larger runs have not been measured, and memory may run out first. Served, that run's page shows its participants but cannot update, since each poll of it takes longer than the 15 seconds the page waits. A participant as busy as the busiest one measured would pass the trace limit in a window of about 27 hours, longer than a window may last, and one at the average rate in about 64.
- `actor.clock.timeZone` or `participants[].clock.timeZone`, a tz database name, adds the local time to every turn and gives the end time in that zone; without it the end time is in UTC. See [give each participant a time zone](#give-each-participant-a-time-zone).

### Let a participant leave before a cap

A `computer-use` participant whose entry sets `maxSessionMs` may end its session whenever it is done, and works no longer than that cap. The cap counts from the start of its own session, after its desktop is set up. In this study visitors arrive every ten minutes, and each stays until it has seen what it came for, for 15 minutes at most:

```yaml
participants:
  - id: visitor
    count: 6
    startEveryMs: 600000 # one every 10 minutes
    maxSessionMs: 900000 # each stays 15 minutes at most
    windDownMs: 120000 # told the time left from 13 minutes in
```

- A participant that ends its own session before its cap counts as it would without one: as passed when it says it reached its goal.
- From `maxSessionMs - windDownMs`, each turn tells the participant when its session ends at the latest and that it may end it sooner. Without `windDownMs` the wind-down is a quarter of the cap, at most 10 minutes: a 10-minute cap is told the time left from 7 minutes 30 seconds in.
- A participant still working at its cap is asked for its closing report, and the session ends as passed, with `stopCause: session_cap` in its trace. The report's summary is the participant's `reason`, and the outcome it declares counts as at a scheduled end: `blocked` counts the participant blocked, and a report that declares `not_reached` or nothing counts it blocked when its summary describes a blocker, and otherwise as running until its session cap.
- Waiting is not the task here: a participant with a cap that only waits or takes screenshots is ended by the idle and no-progress backstops, as one without a cap is.
- The participant's session lasts its cap plus 5 minutes for the closing report, in place of `execution.timeoutMs`, and its sandbox lives that long plus the setup and teardown time. A cap whose sandbox would outlive the [sandbox ceiling](/docs/what-a-study-costs#set-the-sandbox-lifetime-your-e2b-plan-allows) is refused before anything is created.
- Each member of a group gets the whole cap from its own start, and a participant that waits for a free slot still gets its whole cap. Its slot is held for the cap plus 5 minutes when the plan works out the schedule.
- The plan refuses `maxSessionMs` beside `endAfterMs` on one participant, since `endAfterMs` holds a participant until a set time and `maxSessionMs` lets it leave sooner, and refuses `maxSessionMs` on `shared-world`.
- Claude as a `local-agent` participant model cannot be asked for a closing report: a participant that reaches its cap ends with the cap as its reason and no closing account, and `study check` and `run` warn about it.
- `study check` prints each participant's window, and the run's plan line shows `cap=<time>`. The bundle estimate counts a capped participant as one that ends itself: 3 minutes, or its cap when shorter.

### Give each participant a time zone

A hosted desktop's browser runs in UTC, so a participant in London told "the call starts at 10:30" would see times in UTC on every page. `actor.clock` gives every participant a time zone, and `participants[].clock` gives one participant its own:

```yaml
actor:
  clock:
    timeZone: Europe/London # the office
participants:
  - id: agent # Europe/London, from actor.clock
  - id: traveller
    clock:
      timeZone: Asia/Tokyo
```

- Each turn tells the participant the local time in its zone, and a scheduled end (`endAfterMs`) or session cap (`maxSessionMs`) is given in that zone.
- On a hosted desktop, humanish launches the participant's browser with `TZ` set to its zone, so every tab and window it opens runs in that zone from the first page load: JavaScript's `Date` and `Intl.DateTimeFormat().resolvedOptions().timeZone` report it.
- On a `desktop-cli` subject, humanish opens the participant's terminal with `TZ` set to its zone, so its shells, `date`, the product under test and a browser started from the terminal run in that zone.
- A browser or terminal the participant opens from the desktop's dock starts without `TZ` and runs in UTC.
- The clock in the hosted desktop's panel, at the top right of every screenshot, shows the same zone. When humanish cannot set it, the run warns and the clock shows UTC.
- The zone is a tz database name such as `Europe/London`, written with its capitals: `europe/london` and `europe/belfast` are refused, since the browser does not find a name in the wrong case and runs in UTC. A UTC offset such as `+05:00` is refused, since a browser's time zone cannot be set to one.
- The local browser runtime (`execution.target: local`) and `RunStudyOptions.inProcess` do not set the browser's zone, so a study that gives a participant a time zone there is refused before anything starts.
- `study check` prints each participant's zone in a `time zones` row, `study show` prints a `time zones:` line, and `run.json` records each participant's `timeZone` on its stream.
- A participant without a zone runs in UTC, its desktop's panel clock shows UTC, and its turns carry no local time.

## Limit spend and time with `caps`

Every route reads the same top-level `caps` block, and each route refuses the keys it does not read. The caps act on humanish's estimates. They are not provider billing limits, and [what a study costs](/docs/what-a-study-costs#set-a-study-budget) explains what they leave out.

| Field              | Type              | Default                            | Meaning                                                                                                                                                                                                                                |
| ------------------ | ----------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `caps.maxUsd`      | number, 0 or more | none                               | `computer-use` and `shared-world`: stop a participant once its estimated model spend passes this. `terminal`: required for a live run, and it must be 0 ([below](#cap-a-terminal-study)).                                              |
| `caps.maxTotalUsd` | number, 0 or more | none                               | `computer-use` and `shared-world`: stop every participant once the study's estimated model spend passes this, and skip, before its desktop is created, a participant whose start comes after that.                                     |
| `caps.maxJobs`     | number, 0 or more | none                               | `terminal`: the billable product jobs the agent may trigger, checked after the session against measured job counts.                                                                                                                    |
| `caps.maxMinutes`  | number above 0    | required for a live `terminal` run | `terminal`: the agent command's time limit. At the default 60-minute [sandbox ceiling](/docs/what-a-study-costs#set-the-sandbox-lifetime-your-e2b-plan-allows), a live run refuses more than 49, or 44 with `subject.product.install`. |

`preview` and `scripted` take no `caps`.

### Cap a terminal study

humanish has no cost source for a terminal study: Codex reports no provider cost, and humanish measures no product, media or payment spend. A positive `caps.maxUsd` could never trip, so a live terminal run refuses it with `HUMANISH_TERMINAL_UNPRICED_CAP`. Set `caps.maxUsd: 0` and bound the run with `caps.maxMinutes`. `caps.maxJobs` has no measured job count to check for the same reason. Adopter-supplied cost sources are planned in [issue 347](https://github.com/danielgwilson/humanish/issues/347).

## Describe a participant in a persona file

A persona file says who a participant is. humanish looks for `<id>.yaml` or `<id>.yml` in `humanish/personas/`, then in the ignored `.humanish/local/personas/`, and a committed file wins. A persona id uses letters, digits, `_` and `-`. `humanish init` writes two examples:

```yaml title="humanish/personas/skeptical-power-user.yaml"
schema: humanish.persona.v1
id: skeptical-power-user
name: Skeptical Power User
summary: A privacy-safe experienced user looking for speed, reversibility, and clear proof.
background: >-
  Robin manages several volunteer projects with spreadsheets and keyboard shortcuts and is at ease
  with advanced options. They want faster tools but have lost work before and care about undoing
  mistakes. They have little patience for repeated friction and stop when a tool keeps getting in
  the way.
traits:
  accessibility_needs: keyboard_first
constraints:
  - Do not use real personal data.
  - Prefer synthetic fixture inputs.
  - Flag unclear recovery paths.
```

| Field                         | Type                        | Default                         | Meaning                                                                                                                                   |
| ----------------------------- | --------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `schema`                      | string                      | none                            | `humanish.persona.v1`.                                                                                                                    |
| `id`                          | string                      | the id the study names          | The persona's id, at most 120 characters.                                                                                                 |
| `name`                        | string                      | the id in title case            | What the participant is called, at most 120 characters.                                                                                   |
| `summary`                     | string                      | none                            | One line about the person. Text past 280 characters is cut with a warning.                                                                |
| `background`                  | string                      | none                            | Who the person is, in as many paragraphs as you need, up to 32 KiB of UTF-8. A larger or empty background stops the run before it starts. |
| `traits`                      | mapping                     | see below                       | Behavior directives, below.                                                                                                               |
| `traits.patience`             | `low`, `medium` or `high`   | `medium` without a `background` | How much friction the participant works through before stopping.                                                                          |
| `traits.technical_confidence` | `low`, `medium` or `high`   | `medium` without a `background` | Whether the participant sticks to visible controls or uses shortcuts and advanced options.                                                |
| `traits.accessibility_needs`  | text, at most 80 characters | none                            | A need the participant works within. `none`, `none declared` and `not applicable` mean none.                                              |
| `constraints`                 | list of strings             | none                            | Rules the participant is told to honor. The first 8 are used, each up to 160 characters.                                                  |

With a `background`, a trait you leave out sends no directive, and a file that sets both a background and `patience` or `technical_confidence` gets a warning to check them for conflicts. Any other field or trait warns and is not sent. An invalid level warns and falls back to `medium`, or to no directive when there is a background.

Each trait becomes one sentence of the participant's instructions:

| Trait                  | Value                       | Sentence the participant receives                                                                                                                         |
| ---------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `patience`             | `low`                       | You are impatient: if you hit repeated friction or stop making progress toward your goal, you are likely to stop. Describe what you actually encountered. |
| `patience`             | `medium`                    | You have moderate patience: you will work through some friction, but may stop if further effort no longer seems worthwhile.                               |
| `patience`             | `high`                      | You are determined: you are willing to spend effort on recovery when the goal matters to you, but may stop at an unrecoverable dead-end.                  |
| `technical_confidence` | `low`                       | You are not technically confident and generally rely on familiar, visible controls. Describe confusion only when you actually encounter it.               |
| `technical_confidence` | `medium`                    | You have moderate technical confidence and generally use straightforward paths through the product.                                                       |
| `technical_confidence` | `high`                      | You are technically confident and comfortable with keyboard shortcuts and advanced options on the surfaces this product gives you.                        |
| `accessibility_needs`  | contains `keyboard_first`   | You prefer keyboard navigation, but can use a pointer when needed. Describe any difficulty you encounter switching between them.                          |
| `accessibility_needs`  | contains `keyboard_only`    | You can only use the keyboard. If an essential control has no discoverable keyboard path, describe where you could not proceed.                           |
| `accessibility_needs`  | mentions terminal or output | You rely on clear terminal output. Describe any difficulty understanding the output you actually encounter.                                               |
| `accessibility_needs`  | anything else               | Your accessibility requirement is: (your text). Use the available interface within this requirement and describe any difficulty you encounter.            |

These sentences are instructions. humanish does not stop a `keyboard_only` participant from using the mouse, and a persona certifies nothing about accessibility. `npx humanish study show <study> --json` prints the persona text each participant receives, and the run records it.

## Replay scripted browser steps [#scripted-browser-scenarios]

A scripted study replays committed browser steps against an app you run on
a loopback URL. The steps come from the scenario named by `scenario` and make
no model requests. Browser steps are public-safe source, so use synthetic fixture
values and committed relative app paths only.

```yaml title="humanish/scenarios/todo-onboarding.yaml"
schema: humanish.scenario.v1
id: todo-onboarding
title: Todo onboarding
persona: synthetic-new-user
goal: Create the first synthetic todo and verify the list updates.
mode: browser
browser:
  startPath: /
  steps:
    - id: open-home
      label: Open the todo app
      action: goto
      path: /
      expect:
        text: Add todo
    - id: enter-todo
      label: Enter synthetic todo text
      action: fill
      selector: input[name="todo"]
      value: Synthetic onboarding task
    - id: create-todo
      label: Create the todo
      action: click
      selector: button[type="submit"]
      expect:
        text: Synthetic onboarding task
        stateChanged: true
```

Supported actions are `goto`, `fill`, `click`, `press`, `assertText`,
`waitForText`, and `waitForSelector`. A `press` step needs `key`, in Playwright's
key syntax (`Enter`, `Tab`, `Control+A`). With a `selector` it focuses that
element and presses the key; without one it presses the key on the focused
element. Supported expectations are `text`, `selectorVisible`, `urlIncludes`,
and `stateChanged`.

Save the scenario as `humanish/scenarios/todo-onboarding.yaml` and point a study at
it. [`humanish/studies/scripted-demo.yaml`](repo:humanish/studies/scripted-demo.yaml)
is a complete example.

```yaml title="humanish/studies/todo-onboarding.yaml"
schema: humanish.study.v3
id: todo-onboarding
route: scripted
mode: live
subject:
  source: app-url
  appUrl: http://127.0.0.1:3000
actor:
  type: scripted-browser
surfaces: [desktop, mobile]
scenario: todo-onboarding
review:
  analysis: false
```

`surfaces: [desktop, mobile]` adds a mobile surface to the desktop one. Without `mode: live` the study is a dry run: it validates the steps
and writes a contract bundle without opening a browser. Post-run analysis is separate
from the steps: when `OPENAI_API_KEY` is set it runs by default, and it is refused when
its estimate exceeds $10. `analysis: false` turns it off, so the study makes no model
requests.

A live run drives a local Chrome or Chromium against your app, so start the app on
`http://127.0.0.1:3000` first. If humanish finds no browser, the run stops with
`HUMANISH_SCRIPTED_BROWSER_MISSING`; set `HUMANISH_BROWSER_COMMAND` to the browser
binary. Chrome keeps a Unix socket under `TMPDIR`, and a socket path holds at most 107
bytes, so when `TMPDIR` is longer than about 60 bytes humanish launches the browser with
`TMPDIR=/tmp`. `--dry-run` checks the steps without either:

```bash
npx humanish run todo-onboarding --dry-run --json --no-open
npx humanish run todo-onboarding --json --no-open
npx humanish verify --run latest --json
```

Traces are stored as JSON under `.humanish/runs/<run>/traces/` and summarized in
the Observer.

## Move files from 0.107

Before 0.108.0 a study was a `humanish.lab.v2` file under a `labs/` folder. humanish
no longer runs those files or reads the `labs/` folders. Running one by name fails
with the command that fixes it:

```text
humanish run failed: humanish/labs/old-study.yaml is a humanish.lab.v2 file in humanish/labs/, which humanish no longer reads. Run humanish migrate humanish/labs/old-study.yaml to convert it and move it to humanish/studies/.
code: HUMANISH_STUDY_V2_UNSUPPORTED
```

A v3 file left in a `labs/` folder fails with `HUMANISH_STUDY_RETIRED_DIRECTORY`, and its
message names the matching `studies/` folder to move it to; `migrate` skips v3 files.
`humanish study list --json` lists each refused file in `retired`, with its code and message. Convert every v2 file at once:

```bash
npx humanish migrate --dry-run
npx humanish migrate
```

`--dry-run` lists each file's destination and every key it moves or drops, with the
dropped values, and writes nothing. `migrate` then rewrites each v2 file as v3 and
moves it from `labs/` to the matching `studies/` folder; a v2 file outside `labs/` is
rewritten in place. Comments move with their keys. A key the v2 file declared but its
route never read is dropped and reported, and a file that uses YAML anchors is refused
with the line number.
