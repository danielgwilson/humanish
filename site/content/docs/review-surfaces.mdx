## Browse in a human terminal

`humanish tui` is the one command built for a person rather than an agent:

```bash
npx humanish tui
```

Arrow keys move, Enter opens, Esc goes back, q quits. There are six screens. Three are the main path: all labs, one lab, one run. The row below the last lab opens **all runs**, every participant working now across every lab. `?` shows the keys, and `c` opens **connections**, the email catch and provider key setup. A run you are watching updates in place, from running to its verdict, without the screen jumping.

- **labs**: every lab in the project, with the ones running now listed first. Each row shows what a live run of it usually takes. A lab that has never run says `never run`, and one with only dry runs says `<n> runs, none live`; dry runs spend nothing and take no time, so they are not averaged.
- **lab**: that lab's history and two ways to start it. A dry run starts on one keypress because it costs nothing. A live run takes two, with the cost shown between them.
- **run**: who is in the run, what each participant is doing now, and how far along it is, with time and money underneath. A terminal cannot show screenshots, so when the run has an Observer file, the run screen's **Open in Observer** action opens it in your browser.

A run started from the TUI is detached: it keeps going if you quit, and it survives a dropped SSH session. The TUI follows it by reading `.humanish/runs/<id>/status.json` and holds no handle on it, so you can quit mid-run, reopen, and find it still there.

## For coding agents and scripts

`tui` requires interactive stdin **and** stdout. It also
refuses detected coding-agent sessions, even when the runner allocates a TTY.

| Situation                                             | JSON `error.code`               | Exit code |
| ----------------------------------------------------- | ------------------------------- | --------- |
| A recognized coding-agent session                     | `HUMANISH_TUI_AGENT_SESSION`    | `2`       |
| Non-interactive stdin or stdout, with no agent marker | `HUMANISH_TUI_REQUIRES_TTY`     | `2`       |
| Interactive human terminal on Node older than 22      | `HUMANISH_TUI_UNSUPPORTED_NODE` | `2`       |

`--json` returns the refusal envelope; it does not turn the TUI into a JSON browser.
Agent detection uses runner environment markers; absence of a marker does not
prove a human is present. `--force` bypasses only the agent-session guard and is
for a person actually at the keyboard. The TTY and Node requirements still apply.

Use these read-only commands to answer the same browsing questions:

```bash
npx humanish lab list --json
npx humanish lab inspect first-run --json
npx humanish runs --json
npx humanish review --run latest --json
npx humanish stats --json
```

`lab list` shows available labs, `lab inspect` shows a lab's source,
`runs` lists run history, and `review` reads an existing run. If there are no runs
yet, create the [keyless evidence preview](/docs#preview-without-keys)
before asking for `latest`.

Starting a run is a separate action. `npx humanish lab run first-run --json --no-open`
creates a keyless preview; replacing `first-run` with a live lab can launch providers
and incur spend. See the [CLI reference](/docs/cli) for all flags.

## Review study findings

Participants and Findings share one Observer workspace. The participant grid,
recordings and original feedback remain available while you review ranked
observations and follow their evidence links.

Supported live studies request analysis by default when the recording finishes;
`review.analysis: false` in the lab turns it off.
[Automatic analysis](https://github.com/danielgwilson/humanish/blob/main/docs/product/automatic-analysis.md)
has the model, the $3 admission limit and the failure behavior. For an existing
recording, inspect the admission estimate, then generate:

```bash
npx humanish analyze --run latest --max-cost 3 --dry-run --json
npx humanish analyze --run latest --max-cost 3 --json
npx humanish observe --run latest
```

Generation sends selected retained text and captures to OpenAI and requires
`OPENAI_API_KEY`; opening Observer never starts it. The review covers intent,
outcome, friction, recovery and participant feedback; each finding links to
original evidence. Coverage limits and missing evidence remain visible.

**Concerns considered** shows material concerns reviewed in the analysis,
including reasons for leaving some out of the ranked findings. Follow those
evidence links to inspect a reported concern or recovered mistake. Reported
confusion may be useful even when a link is correct or the study setup explains
it; the finding should qualify its cause. These decisions are model
interpretations and still need review.

`analyze list --json` includes version history and execution receipts.
`analyze show --json` reads the latest usable version. Use `--rerun` to request
a new version, or `--question` for an additional reviewer question.

```bash
npx humanish analyze correct --run latest --analysis <id> --finding F1 --status confirmed --reason "The cited captures reproduce the issue."
npx humanish feedback issue --run latest --analysis <id> --finding F1 --repo owner/repo
```

Corrections are bound to the exact version reviewed. Feedback still requires
share-ready evidence. Redacted exports omit analysis that refers to original
source hashes; analyze the derived run again.

**Replay for an audience.** Open the Observer artifact with
`?autoplay=8&loop=1&sidebar=closed` before the `#` and it presses play on the
study transport at 8x as soon as the recording loads, restarts two seconds
after the last capture, and starts with the library collapsed. `autoplay`
alone means 8x; any value from 1 to 64 works; `sidebar=closed` also works on its
own. Every control still works, and a viewer who pauses stays paused. This is
how humanish.dev embeds a saved run.

## Serve the run library

`humanish watch` follows one attached run; `humanish serve` serves the whole
local run library under `.humanish/runs/`, a library index plus every run's
Observer page:

```bash
npx humanish serve
npx humanish serve --expose --tunnel ngrok --oauth google --allow-email you@example.com
npx humanish serve --safe --expose --tunnel ngrok
npx humanish serve --expose --public-url https://observer.example.com
```

The first serves the library on loopback only. The second is the phone path:
ngrok's edge authenticates viewers with Google OAuth (restricted to your
`--allow-email`/`--allow-domain` allow rules) before any request reaches the
loopback server; humanish carries no in-process auth. The third is a secretless
safe observer: no login, but only runs whose `humanish verify` shareSafety is
`share_ready` exist at all; everything else is absent and 404s. A run is verified
again before it is served whenever any of its files changes, so a file added or
rewritten after verification is not served until the run grades `share_ready`
again. [Verify before sharing](/docs/read-results#verify-before-sharing) lists what
keeps a run from `share_ready`. The fourth
trusts an edge you already secure (Cloudflare Access, Tailscale, a proxy you own)
and just binds loopback behind it.

In every mode the server binds `127.0.0.1`. `--expose` is refused before binding
unless it has a reachable origin and either edge auth or `--safe`; the
[exposure matrix](https://github.com/danielgwilson/humanish/blob/main/docs/architecture/serve.md#fail-closed-exposure-matrix)
lists each combination and its error code.

## Watch a live run from your phone

`humanish watch <cua-lab> --expose --tunnel ngrok --oauth google --allow-email
you@example.com` streams the live desktop of a computer-use run to an
edge-authenticated remote viewer while it plays. The attached server comes up
during the run and survives a timed-out/failed run, so you can inspect a failed
run's evidence too. A live run is never `share_ready`, so `watch --expose` always
requires edge auth; `--safe` is a `serve` library filter and is rejected on watch
(`HUMANISH_WATCH_SAFE_NOT_APPLICABLE`). An exposed watch serves only the attached
run (its history lists just that run and every other run id 404s), so a remote
viewer can never reach your other runs' raw evidence.

Live E2B desktop stream URLs reach a remote viewer only on `watch --expose`, and only
behind edge auth; `serve` never injects them (remote viewers of the library see only
persisted evidence: screenshots, events, terminal tails). See
[Serve architecture](https://github.com/danielgwilson/humanish/blob/main/docs/architecture/serve.md).
